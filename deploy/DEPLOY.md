# Деплой aiethos.ru на сервер

Сайт — Next.js (App Router). Все страницы статические, но раздаются через
`next start` (Node) за nginx-реверс-прокси. HTTPS — Let's Encrypt (certbot).

- **Сервер:** `72.56.5.23`
- **Домен:** `aiethos.ru`
- **Репозиторий:** https://github.com/eeephemera/ethos.git
- **Ветка:** `claude/deploy-ethos-server-nigp2j`

---

## ⚠️ Сначала — DNS

На момент подготовки `aiethos.ru` указывал на `83.217.220.10`, а не на сервер
`72.56.5.23`. **HTTPS не выпустится**, пока A-запись не будет указывать на сервер.

В панели управления доменом задайте:

| Тип | Имя   | Значение      |
|-----|-------|---------------|
| A   | `@`   | `72.56.5.23`  |
| A   | `www` | `72.56.5.23`  |

Подождите распространения DNS (обычно минуты, максимум пара часов). Проверить:

```bash
dig +short aiethos.ru        # должно вернуть 72.56.5.23
```

## Деплой одной командой

Зайдите на сервер и выполните:

```bash
ssh root@72.56.5.23

apt-get update && apt-get install -y git
git clone https://github.com/eeephemera/ethos.git /opt/ethos
cd /opt/ethos
git checkout claude/deploy-ethos-server-nigp2j

# email нужен для автоматического выпуска сертификата (можно опустить и выпустить вручную)
CERTBOT_EMAIL="you@example.com" bash deploy/deploy.sh
```

Скрипт `deploy/deploy.sh`:

1. Ставит Node.js 22, nginx, git, certbot.
2. Собирает приложение (`npm ci && npm run build`).
3. Ставит и запускает systemd-сервис `ethos` (слушает `127.0.0.1:3000`).
4. Ставит nginx-конфиг реверс-прокси для `aiethos.ru`.
5. Если DNS уже указывает на сервер — выпускает HTTPS-сертификат и включает редирект на https.

Повторный запуск безопасен: подтянет свежий код, пересоберёт и перезапустит.

## Что происходит под капотом

| Компонент       | Файл                          | Назначение                                |
|-----------------|-------------------------------|-------------------------------------------|
| systemd         | `deploy/ethos.service`        | Держит `npm run start` живым на порту 3000 |
| healthcheck     | `deploy/ethos-health.*`       | Каждые 2 мин проверяет порт, перезапускает при зависании |
| nginx           | `deploy/nginx-aiethos.conf`   | Реверс-прокси 80/443 → 127.0.0.1:3000     |
| certbot         | (ставится скриптом)           | Сертификат Let's Encrypt + авто-редирект  |
| swap            | `/swapfile` (2G)              | Защита от OOM-падений на VPS с малой RAM   |

## Отказоустойчивость (чтобы сервис не падал)

`deploy.sh` настраивает самовосстановление:

1. **systemd `Restart=always`** — сервис перезапускается при любом падении (краш,
   OOM, ошибка) через 3 сек, без лимита попыток (`StartLimitIntervalSec=0`).
2. **Автозапуск при загрузке** — `systemctl enable ethos`: сервис поднимается сам
   после перезагрузки сервера.
3. **Healthcheck-сторож** (`ethos-health.timer`) — каждые 2 минуты дергает
   `http://127.0.0.1:3000`; если приложение зависло (живо, но не отвечает) —
   перезапускает его. systemd сам такое не ловит.
4. **Swap 2 ГБ** — не даёт ядру убивать Node при пике памяти (частая причина
   падений на VPS с 1–2 ГБ RAM).

Проверить состояние:

```bash
systemctl status ethos              # активен ли сервис
systemctl status ethos-health.timer # работает ли сторож
journalctl -u ethos -n 50 --no-pager
swapon --show                       # включён ли swap
```

Быстрый тест самолечения — «убить» приложение и увидеть, что оно вернулось:

```bash
systemctl kill -s SIGKILL ethos && sleep 5 && systemctl is-active ethos   # -> active
```

## Полезные команды

```bash
# логи приложения
journalctl -u ethos -f

# перезапуск после ручных изменений
systemctl restart ethos

# проверка, что Node-сервер отвечает локально
curl -I http://127.0.0.1:3000

# проверка/перезагрузка nginx
nginx -t && systemctl reload nginx

# выпустить сертификат вручную (после настройки DNS)
certbot --nginx -d aiethos.ru -d www.aiethos.ru

# обновить сайт до свежего коммита
cd /opt/ethos && bash deploy/deploy.sh
```

## HTTPS: сертификат выпущен через DNS-01

На этом сервере публичный IP `72.56.5.23` доступен по порту 80 **не из всех
регионов** (проверка `check-host.net` показала таймауты из США/Азии/части ЕС —
особенность сети провайдера). Поэтому обычная проверка Let's Encrypt по HTTP
(`--nginx` / HTTP-01) **не проходит** — валидатор LE не достаёт до сервера.

Сертификат выпущен методом **DNS-01** (подтверждение через TXT-запись, порт 80
не нужен):

```bash
# 1) запросить сертификат — certbot покажет значение для TXT-записи
certbot certonly --manual --preferred-challenges dns \
  --agree-tos -m <email> -d aiethos.ru

# 2) в DNS-панели добавить TXT-запись:
#      Хост: _acme-challenge     Значение: <выданное certbot>
#    дождаться распространения:  dig +short TXT _acme-challenge.aiethos.ru @8.8.8.8
# 3) вернуться в certbot и нажать Enter

# 4) подключить сертификат к nginx (редирект http->https)
certbot install --nginx -d aiethos.ru
```

⚠️ **Продление не автоматическое** (DNS-01 вручную). Сертификат действует 90
дней — перед истечением повторить шаги 1–3 (значение TXT будет новым). Автопродление
можно настроить через `--manual-auth-hook` с API DNS-провайдера (Timeweb) — при
необходимости.

## Несколько проектов на одном сервере (ethos + domostroy)

Посмотреть, что уже занято и нет ли конфликтов:

```bash
cd /opt/ethos && bash deploy/audit-server.sh
```

Схема сосуществования: **один nginx спереди, приложения на разных
внутренних портах**.

```
        :80 / :443           nginx (единственный, кто держит эти порты)
                               ├── server_name aiethos.ru    -> 127.0.0.1:3000  (ethos)
                               └── server_name domostroy.??  -> 127.0.0.1:3001  (domostroy)
```

Три правила, чтобы проекты не конфликтовали:

1. **Разные внутренние порты.** ethos по умолчанию на `3000`. Если он занят
   domostroy — разверните ethos на другом порту, скрипт сам всё пропишет
   (и в systemd, и в nginx, и в healthcheck):
   ```bash
   APP_PORT=3001 bash deploy/deploy.sh
   ```
   `deploy.sh` откажется стартовать, если порт занят чужим процессом.
2. **Разные `server_name`** в отдельных файлах `/etc/nginx/sites-available/`.
   Один домен не должен встречаться в двух конфигах — `audit-server.sh` это проверяет.
3. **Свой сертификат на каждый домен.** `certbot --nginx -d <домен>` трогает
   только тот конфиг, где этот `server_name`.

> ⚠️ Ранее `deploy.sh` безусловно удалял `/etc/nginx/sites-enabled/default`.
> Если domostroy отдавался через дефолтный сайт, он мог отключиться. Сейчас
> скрипт удаляет default только если это нетронутая заглушка Ubuntu.
> Проверить, что domostroy жив: `bash deploy/audit-server.sh`.

**Нужен ли Docker?** Он изолирует зависимости и версии Node, но **не решает
конфликт за порты 80/443** — они всё равно одни на сервере, и разводит домены
всё тот же nginx. Контейнер имеет смысл, если у проектов разные версии
Node/Python или нужны лимиты по памяти; для «чтобы не конфликтовали» достаточно
разных портов и разных `server_name`.

## «У меня открывается, а у других нет»

Классическая ситуация: сайт работает на одном компьютере и не открывается у людей
в другой сети / с телефона / через VPN. Причины идут в таком порядке:

**1. Сначала — диагностика на сервере:**

```bash
cd /opt/ethos && bash deploy/diagnose-network.sh
```

Скрипт проверит сервис, порты, DNS, цепочку TLS-сертификата, firewall и MTU.

**2. MTU / MSS (самая частая «сетевая» причина).**
У мобильного интернета и VPN MTU меньше стандартного. Соединение
устанавливается, но крупные пакеты молча теряются → страница висит и не
грузится. У кого MTU обычный — сайт открывается. Лечится включением MSS clamping:

```bash
bash deploy/fix-mtu.sh
```

(с версии этого скрипта `deploy.sh` включает clamping автоматически)

**3. `www.aiethos.ru`.**
Если A-записи для `www` нет — у тех, чей браузер подставляет `www.`, сайт не
откроется вовсе. Если запись есть, но сертификат её не покрывает — будет
предупреждение о безопасности. Нужно и то, и другое: A-запись `www → 72.56.5.23`
**и** сертификат на оба домена:

```bash
certbot certonly --manual --preferred-challenges dns \
  --agree-tos -m <email> -d aiethos.ru -d www.aiethos.ru
certbot install --nginx -d aiethos.ru
```

(certbot попросит **две** TXT-записи `_acme-challenge` — добавьте обе)

**4. Неполная цепочка сертификата.**
Настольные браузеры умеют дотягивать промежуточный сертификат сами, а телефоны —
нет. Если `diagnose-network.sh` пишет, что отдаётся только 1 сертификат, в nginx
должен быть именно `fullchain.pem`, а не `cert.pem`.

**5. Маршрутизация провайдера.**
Если всё выше в порядке, а из части стран/сетей всё равно таймаут — проверьте:

```
https://check-host.net/check-http?host=https://aiethos.ru
https://check-host.net/check-tcp?host=aiethos.ru:443
```

Массовые «Connection timed out» = проблема на стороне Timeweb (анонс сети,
фильтрация, репутация IP). Решается только через их поддержку: приложить отчёт
check-host и попросить проверить доступность IP извне либо выдать другой адрес.

## Обновление сайта (после изменений в коде)

`deploy.sh` теперь **не трогает** nginx-конфиг и сертификат, если Certbot уже
настроил HTTPS, поэтому его можно запускать повторно. Но для чистого обновления
кода достаточно:

```bash
cd /opt/ethos && git pull
cd nextjs && npm ci && npm run build
systemctl restart ethos
```
